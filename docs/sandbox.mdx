The sandbox gives your agent a secure, isolated environment to run code, manipulate files, and execute shell commands — separate from the TrueForge server and your infrastructure.

Skills and [Code Mode](/key-features/code-mode) require a sandbox. Configure a provider once under **Settings → Sandbox providers**, then enable the sandbox on each agent that needs it.

## TrueForge's approach

There are two common patterns for combining agents with sandboxes:

| Pattern | Where the agent runs | Trade-off |
| --- | --- | --- |
| **Agent in sandbox** | Inside the sandbox image | Sandbox is provisioned even for the simplest request; secrets must live in the sandbox; updates mean rebuilding images |
| **Sandbox as tool** | Outside, on the server | Sandbox is provisioned on demand when needed; secrets stay in the harness; sandbox is only for exec/files |

TrueForge uses **sandbox as tool**: the agent loop and credentials stay in the harness; the sandbox only runs code, file, and shell operations.

That means:

- Model and MCP credentials never enter the sandbox.
- Conversation state survives a sandbox crash.
- A sandbox is created only when the agent actually needs one — simple Q&A and MCP calls incur no sandbox cost.

## Configuring a provider

The Settings UI currently exposes the [Daytona](https://www.daytona.io) provider. Hosted deployments can also use
the Kubernetes provider through environment configuration; Kubernetes is not yet part of the Settings UI or the
generated OpenAPI schema.

Open **Settings → Sandbox providers**, pick the [Daytona](https://www.daytona.io) preset from the catalog, and paste your API key.

<Note>
  The Daytona API key needs permission to create **snapshots**, not only sandboxes. The first time you configure the
  provider, TrueForge builds a release snapshot in your Daytona account, and every sandbox it starts afterwards is
  cloned from that snapshot. Create the key with **Sandboxes** access and **Snapshots** write (create) permission.

  If the key is missing snapshot permission, configuring the provider fails 
  even though the key is otherwise valid. If you hit that, check the key's permissions before regenerating it.
</Note>

## Kubernetes provider

The Kubernetes provider is for hosted or distributed deployments. It creates one sandbox workload per session from
TrueForge's pinned sandbox image and uses the cluster's credentials instead of an API key. Set these values on the
TrueForge server:

```dotenv
STANDALONE=false
TRUEFOUNDRY_SANDBOX_ENABLED=true
TRUEFOUNDRY_SANDBOX_PROVIDER=kubernetes
KUBERNETES_SANDBOX_NAMESPACE=trueforge-sandboxes
KUBERNETES_SANDBOX_IN_CLUSTER=true
KUBERNETES_SANDBOX_SERVICE_ACCOUNT_NAME=trueforge-sandbox
KUBERNETES_SANDBOX_EXEC_TIMEOUT_MS=60000
KUBERNETES_SANDBOX_POLL_INTERVAL_MS=1000
KUBERNETES_SANDBOX_CREATE_TIMEOUT_MS=120000
KUBERNETES_SANDBOX_REAPER_TTL_MS=86400000
```

`KUBERNETES_SANDBOX_IMAGE_PULL_SECRET_NAME` is needed when the cluster cannot pull the pinned sandbox image without
registry credentials. Resource requests and limits can be supplied as JSON in
`KUBERNETES_SANDBOX_RESOURCES`, for example:

```dotenv
KUBERNETES_SANDBOX_RESOURCES={"requests":{"cpu":"500m","memory":"512Mi"},"limits":{"cpu":"1","memory":"1Gi"}}
```

`TRUEFOUNDRY_SANDBOX_SETTINGS` may be `{}` for Kubernetes, or may contain a `resources` object. If both settings
locations define resources, `KUBERNETES_SANDBOX_RESOURCES` takes precedence.

When the Agent Sandbox controller and `sandboxes.agents.x-k8s.io` CRD are installed, TrueForge uses the CR backend.
Without that CRD it falls back to labelled Pods. Both paths use the same provider contract, sandbox image, and
storage: session files live in an `emptyDir` mounted over the sandbox's working directory, so they survive a
container restart but not the pod being rescheduled.

The server's Kubernetes identity needs permission to create, get, list, and delete Pods, create `pods/exec`, and create
`pods/portforward` when `KUBERNETES_SANDBOX_IN_CLUSTER=false`. It also needs to read the
`sandboxes.agents.x-k8s.io` CRD and, when the CRD is installed, create, get, list, and delete `sandboxes` resources.

For an external server, set `KUBERNETES_SANDBOX_IN_CLUSTER=false` and make the server's kubeconfig available. The
provider opens a local port-forward to the sandbox for Code Mode. For an in-cluster server, set it to `true` so Code
Mode connects directly to the sandbox Pod IP.

### Test the provider before opening a PR

The contract suite exercises creation, command execution, file upload/download, layout paths, and Code Mode. Run it
against a disposable kind cluster with the Agent Sandbox controller installed:

```bash
kind create cluster --name trueforge-sandbox
kubectl apply --server-side \
  -f https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.2/sandbox.yaml
kubectl wait --for=condition=Established \
  crd/sandboxes.agents.x-k8s.io --timeout=120s
kubectl wait --for=condition=Available \
  deployment/agent-sandbox-controller -n agent-sandbox-system --timeout=180s

export KUBERNETES_SANDBOX_NAMESPACE=default
export KUBERNETES_SANDBOX_IN_CLUSTER=false
pnpm test:kubernetes-sandbox:contract
```

To exercise the raw Pod fallback, create a second disposable cluster and do not install the Agent Sandbox manifest:

```bash
kind create cluster --name trueforge-sandbox-pod
kubectl config use-context kind-trueforge-sandbox-pod
export KUBERNETES_SANDBOX_NAMESPACE=default
export KUBERNETES_SANDBOX_IN_CLUSTER=false
pnpm test:kubernetes-sandbox:contract
```

Delete the test clusters when finished:

```bash
kind delete cluster --name trueforge-sandbox
kind delete cluster --name trueforge-sandbox-pod
```

If the contract suite reports an image-pull error, configure `KUBERNETES_SANDBOX_IMAGE_PULL_SECRET_NAME` and create
the matching `docker-registry` Secret in the sandbox namespace before rerunning it.

## Enabling the sandbox on an agent

The sandbox is **off by default** per agent. Turn it on in the agent builder when you need code execution, skills, or Code Mode. You can also set `config.sandbox.enabled` in the [agent spec](/create-agent/overview#config) when creating agents via the SDK.

Optional controls:

- **File downloads** — let users download files the agent produces (on by default in the chat UI).

## Lifecycle

- Provisioned on demand when the agent needs code, files, skills, or Code Mode.
- Reused across turns in the same session (files persist).
- Stopped after idle time, then archived and eventually deleted per the provider settings.

## Credential safety

- Model and MCP credentials stay in the harness.
- MCP calls from [Code Mode](/key-features/code-mode) scripts are bridged back to the harness — the sandbox never holds those tokens.
