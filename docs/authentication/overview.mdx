TrueForge authentication is optional. For local use you can leave it off. For a shared team deployment, turn on OIDC so people sign in with your identity provider and Settings stay admin-only.

## Choose your mode

| Mode | When to use | What users see |
| --- | --- | --- |
| **No login** | Local `npx`, trusted networks | No login screen; everyone is a fixed local admin |
| **OIDC login** | Hosted / shared teams | Sign-in with your IdP; roles `admin` or `user` |

Standalone / local mode ignores OIDC even if env vars are present.

## Guide: leave auth off (local)

1. Do **not** set `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, or `OIDC_CLIENT_SECRET`.
2. Run TrueForge as usual ([Quickstart](/quickstart)).
3. Open the UI — there is no login screen. Settings and chat are available immediately.

Use this only on localhost or behind network controls you trust. On a public host, anyone who can reach the server gets admin Settings access under one shared identity.

## Guide: enable OIDC for your team

### 1. Prepare your identity provider

Create a **confidential (Web)** OIDC app with:

- Grant type **Authorization Code** (PKCE is also used)
- Redirect URI: `{PUBLIC_BASE_URL}/api/v1/auth/callback`
- Users/groups allowed to sign in
- ID token claims for identity and admin membership (see below)

Public / SPA clients are not supported — TrueForge needs a client secret.

Provider-specific steps: [Okta](/authentication/okta).

### 2. Set server environment

Set all three OIDC variables together (partial config fails startup), plus the public origin:

| Variable | Required | Purpose |
| --- | --- | --- |
| `PUBLIC_BASE_URL` | yes | Public origin users and the IdP see (no trailing path) |
| `OIDC_ISSUER_URL` | yes* | IdP issuer (discovery at `/.well-known/openid-configuration`) |
| `OIDC_CLIENT_ID` | yes* | OIDC client ID |
| `OIDC_CLIENT_SECRET` | yes* | OIDC client secret |
| `OIDC_USER_REFERENCE_CLAIM` | no (default `sub`) | Claim used as the user id for session ownership |
| `OIDC_USER_ROLE_CLAIM` | no (default `groups`) | Claim inspected for admin membership |
| `OIDC_ADMIN_ROLE_VALUE` | no (default `admin`) | Exact string that grants `admin` (case-sensitive) |
| `OIDC_SCOPES` | no (default `openid,profile,email`) | Scopes for the authorize request |

\*Required when enabling OIDC; otherwise leave all three unset.

In Helm, set `server.publicBaseUrl` and pass `OIDC_*` through `server.extraEnv` / `server.extraEnvFrom`. Keep the client secret in a Kubernetes Secret.

### 3. Map admin vs user

| Role | Who | What they can do |
| --- | --- | --- |
| **admin** | Role claim contains `OIDC_ADMIN_ROLE_VALUE` | Chat + change Settings (models, connectors, skills, sandbox) |
| **user** | Everyone else who can sign in | Chat and use agents; Settings hidden |

Session history is still owner-only — admins are not global session superusers today. The [Agent Library](/agent-library) is currently shared: agents created by anyone are visible to everyone on the instance.

### 4. Sign in and verify

1. Open the UI — you should get the IdP login.
2. After login, confirm admins see **Settings** and non-admins do not.
3. If someone expected admin but got user, decode their ID token and check the role claim value (exact, case-sensitive). Sign out and back in after IdP claim changes.

### 5. Call the API with a token (optional)

The UI stores an HttpOnly cookie after login. For the [SDK](/api/overview), send the same ID token as `Authorization: Bearer <id_token>`. Obtain the token from your IdP (or reuse a browser session); there is no device/client-credentials flow yet.

Keep ID token lifetimes short at the IdP — the same JWT unlocks the API as cookie or Bearer.

## Security checklist

- Prefer secrets storage for `OIDC_CLIENT_SECRET`; do not commit it.
- Do not expose a no-OIDC deployment on the public internet.
- Register the exact callback URL your users hit (scheme + host).
