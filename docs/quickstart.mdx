## Run TrueForge

TrueForge runs in [two modes](/introduction#two-ways-to-run-it): **local mode** — a single process on your machine, like a personal productivity tool — and **hosted mode** — a shared deployment for your team, with Postgres for storage and Redis for cross-replica peering. The agent features are identical in both.

<Tabs>
  <Tab title="Local mode (npx)">
    Requires [Node.js](https://nodejs.org) 22.13 or newer. One command, no other infrastructure — the UI and backend run locally, and data is stored in a local SQLite file:

    ```bash
    npx @truefoundry/trueforge
    ```

    Then open [http://localhost:8790](http://localhost:8790). The defaults work out of the box — see the [FAQ](#faq) to change the port or data location.

  </Tab>
  <Tab title="Hosted mode (Docker Compose)">
    Runs the full hosted topology on your machine: the server (UI + API), Postgres, and Redis.

    ```bash
    git clone https://github.com/truefoundry/trueforge && cd trueforge
    cp packages/server/.env.example packages/server/.env
    docker compose up --build
    ```

    Then open [http://localhost:8791](http://localhost:8791).

    | Configuration                                         | Default                 | Description                                              |
    | ----------------------------------------------------- | ----------------------- | -------------------------------------------------------- |
    | `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | from `.env`             | Postgres credentials, read from `packages/server/.env`.  |
    | `PUBLIC_BASE_URL`                                     | `http://localhost:8791` | Public origin, used for MCP OAuth callbacks.             |
    | Host ports                                            | `8791`, `5433`, `6380`  | App, Postgres, and Redis.                                |

  </Tab>
  <Tab title="Hosted mode (Kubernetes)">
    The Helm chart deploys the server in hosted mode with bundled Postgres and Redis (or point it at your own). No values are required for a basic install:

    ```bash
    # TODO: replace <HELM_REPO> with the published Helm repo URL
    helm install truefoundry-utils oci://<HELM_REPO>/truefoundry-utils \
      --version <x.y.z>
    ```

    | Value                  | Default | Description                                                             |
    | ---------------------- | ------- | ------------------------------------------------------------------------ |
    | `server.publicBaseUrl` | `""`    | Public origin for MCP OAuth / OIDC callbacks; set once you expose the service. |
    | `replicaCount`         | `1`     | Number of server replicas (peered over Redis).                           |
    | `postgresql.enabled`   | `true`  | Bundle Postgres; set `false` + `externalPostgres.*` to bring your own.   |
    | `redis.enabled`        | `true`  | Bundle Redis; set `false` + `externalRedis.url` or `existingSecret`.     |

  </Tab>
</Tabs>

<Note>
  Local mode (`npx`) uses SQLite and needs no other services. Docker Compose and Kubernetes run hosted mode: Postgres
  replaces SQLite as durable storage, and Redis peers the replicas so streams and cancellations follow the client
  across them.
</Note>

## Build your first agent

With TrueForge open in your browser, this walkthrough takes you from an empty workspace to a saved, reusable agent. The example builds a **GitHub repo explainer** — an agent that turns any public repo into a one-page PDF brief.

<Steps>
  <Step title="Add a model provider">
    Open **Settings → Models**, pick a provider from the catalog, and paste your API key. Its models become available immediately — no restart needed.

    <Frame>
      <img src="/images/quickstart-models.png" alt="Settings → Models with the OpenAI provider expanded, showing an API key field and a Create button" />
    </Frame>
  </Step>

  <Step title="Connect a tool">
    Open **Settings → Connectors** and connect a [Model Context Protocol (MCP)](/mcp-servers) server so your agent can reach external tools and data. Pick one from the catalog and click **Connect** (via OAuth, an API key, or no auth), or use **Add MCP Server** to register your own by URL.

    <Frame>
      <img src="/images/quickstart-connectors.png" alt="Settings → Connectors with deepwiki connected, above a catalog of more MCP servers to connect" />
    </Frame>
  </Step>

  <Step title="Add a skill">
    Open **Settings → Skills**. Select a built-in skill, or click **Import from GitHub** to add a [git-backed skill](/skills) from any repository.

    <Frame>
      <img src="/images/quickstart-skills.png" alt="Settings → Skills: a selected skill and an available skill with a Select button, plus an Import from GitHub action" />
    </Frame>
  </Step>

  <Step title="Add a sandbox provider (optional)">
    A [sandbox](/sandbox) lets the agent run code, work with files, and use skills. TrueForge supports [Daytona](https://www.daytona.io) today. It's a one-time setup:

    1. **Create a Daytona API key** with permission to write and delete snapshots and write sandboxes.
    2. **Sync the TrueForge sandbox image** to your Daytona account (a one-time CLI step).
    3. **Add the provider** under **Settings → Sandbox providers** — choose Daytona and enter your API key and snapshot name.

    <Frame>
      <img src="/images/quickstart-sandbox.png" alt="The Daytona sandbox provider dialog with snapshot name, exec timeout, lifecycle intervals, and an API key field" />
    </Frame>

    See the [Sandbox guide](/sandbox) for the exact API-key permissions and the image-sync command.
  </Step>

  <Step title="Compose an agent and start chatting">
    Back in the chat, assemble the agent for this conversation, then send your first message.

    1. **Pick a model** from the selector in the composer.
    2. Open the **+** menu → **Connectors** and enable the MCP server you connected.
    3. In the same menu → **Skills**, enable your skill.
    4. Send your message. Streaming, tool calls, sandbox output, and [approvals](/human-in-the-loop) all show up live.

    <Frame caption="Pick a model, then add your connector and skill to the turn from the + menu.">
      <img src="/images/quickstart-composer-connectors.png" alt="The composer with a model selected and the + menu open on the Connectors tab, a connector checked" />
    </Frame>
    <Frame caption="The agent runs — here it used the connector, the sandbox, and the pdf skill to generate a one-page brief.">
      <img src="/images/quickstart-chat-result.png" alt="A completed chat where the agent generated a one-page PDF brief, with one connector and one skill active" />
    </Frame>
  </Step>

  <Step title="Save it as an agent">
    Happy with the setup? Click **Save as agent**, give it a name and system instructions, and **Save**. This captures the model, connectors, skills, and prompt together as a reusable agent.

    <Frame>
      <img src="/images/quickstart-save-agent.png" alt="The Save as agent dialog with a name and system instructions" />
    </Frame>
  </Step>

  <Step title="Find it in the Agents Library">
    Open **Agents Library** from the sidebar. Your saved agent is there — click **Try** to start a fresh chat with the same setup, or **Edit** to tweak it.

    <Frame>
      <img src="/images/quickstart-agents-library.png" alt="The Agents Library listing the saved github-repo-explainer agent with Edit and Try actions" />
    </Frame>
  </Step>
</Steps>

Everything you configure in Settings is also available through the API — see the interactive docs at `/api/v1/docs`.

## Call the API

Every conversation in the UI is a session in the API. Create one yourself:

```bash
curl -X POST http://localhost:8790/api/v1/sessions \
  -H 'Content-Type: application/json' \
  -d '{
    "agent": {
      "type": "value",
      "agent_spec": {
        "model": { "name": "anthropic/claude-sonnet-4-6" },
        "instructions": "You are a helpful assistant."
      }
    }
  }'
```

Then start a turn and stream events over SSE:

```bash
curl -N -X POST http://localhost:8790/api/v1/sessions/{session_id}/turns \
  -H 'Content-Type: application/json' \
  -d '{
    "input": [{ "type": "user.message", "content": "Hello!" }]
  }'
```

See the [API overview](/api/overview) for the full lifecycle — turn chaining, approvals, and event handling.

## FAQ

<AccordionGroup>
  <Accordion title="How do I run the server on a different port?">
    Pass `--port`, or set the `PORT` environment variable:

    ```bash
    npx @truefoundry/trueforge --port 3000
    # or
    PORT=3000 npx @truefoundry/trueforge
    ```

    In hosted mode, change the host port mappings in `docker-compose.yml` instead.

  </Accordion>
  <Accordion title="Where does local mode store its data?">
    In a SQLite file in your OS's application data directory. To put it somewhere else, set the `SQLITE_PATH` environment variable:

    ```bash
    SQLITE_PATH=~/trueforge/db.sqlite npx @truefoundry/trueforge
    ```

  </Accordion>
  <Accordion title="What is PUBLIC_BASE_URL and when do I need to set it?">
    The public origin the server hands to MCP servers for OAuth callbacks. It defaults to `http://localhost:<port>`, which is correct as long as you access TrueForge from the same machine.

    Set it when the server is reachable at a different address — behind a domain, reverse proxy, or on another host:

    ```bash
    PUBLIC_BASE_URL=https://agents.example.com npx @truefoundry/trueforge
    ```

    In hosted mode, set it in `packages/server/.env` (Docker Compose) or via `server.publicBaseUrl` (Helm).

  </Accordion>
</AccordionGroup>
