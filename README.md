# TrueFoundry harness workspace

pnpm workspace with:

| Package               | Path                                     | Role                                             |
| --------------------- | ---------------------------------------- | ------------------------------------------------ |
| `@truefoundry/utils`  | [`packages/harness`](packages/harness)   | Published library (`core` + `agent-session`)     |
| `@truefoundry/server` | [`packages/server`](packages/server)     | HTTP server (private; depends on utils)          |
| `frontend`            | [`packages/frontend`](packages/frontend) | Private draft-only agent chat UI (not published) |

## Develop

```bash
pnpm install
pnpm build
pnpm test
pnpm typecheck
```

Root `build` / `typecheck` (and CI) include utils, server, and frontend.

## Run the server

Create the local environment and registry files from the tracked examples:

```bash
cp packages/server/.env.example packages/server/.env
cp -R packages/server/registry-example packages/server/registry
```

Fill in `MODEL_API_KEY` in `packages/server/.env`, then start the server:

```bash
pnpm dev:server
```

Migrations run automatically on startup. To migrate without starting HTTP:

```bash
pnpm --filter @truefoundry/server migrate
```

## Run the frontend (local)

With the server on `:8790`:

```bash
pnpm dev:frontend
```

Vite serves the UI on `http://localhost:3000` and proxies `/v1/agents/*` → `/v1/sessions*` plus catalog routes. See [`packages/frontend/README.md`](packages/frontend/README.md).

## Docker Compose

```bash
docker compose up --build
```

Starts Postgres 17 (data in `./data/postgres`), the API, and the frontend. The server waits for Postgres to be healthy, runs migrations, then listens.

- API: `http://localhost:8790`
- UI: `http://localhost:3000` (Caddy proxies same-origin `/v1/...` to `server:8790`)

The local `.env` file, `packages/server/registry/`, and `data/` are ignored by Git. Docker Compose requires `packages/server/.env` and mounts the registry read-only into the server container.

## SDK generation

`packages/sdk` holds the TypeScript SDK, generated by [Fern](https://buildwithfern.com) from
`fern/openapi/openapi.json`. Both are generated and committed — edit the route definitions in
`packages/server/src/routes/`, never the output.

The OpenAPI document is produced from the server's route definitions without starting the server:

```bash
pnpm openapi:write
```

Fern names SDK methods from the `x-fern-sdk-group-name` / `x-fern-sdk-method-name` extensions on
each `createRoute(...)`, since this server sets no `operationId`. `pnpm openapi:write` fails if an
operation is missing them. Pagination and SSE are declared the same way, via
`packages/server/src/routes/fernExtensions.ts`.

To regenerate the SDK locally you need Docker:

```bash
npm install -g fern-api@5.82.0
fern check
fern generate --group ts-sdk --version 0.0.0 --local --generate-tests
```

Both flags matter. `--local` runs the generator image here rather than on Fern's infrastructure, and
`--generate-tests` is what makes the output a publishable package instead of loose source files: Fern
writes a manifest, tsconfigs and tests only when its internal `generateFullProject` flag is set, which
locally resolves to `generateTests || selfHostedSDKs`.

A remote run cannot substitute for this. It derives the same flag from the `selfHostedSDKs`
entitlement alone and ignores `--generate-tests`, and that entitlement is off for the `truefoundry`
organization, so a remote run emits source files with no `package.json`. The workflow therefore
generates locally and needs no `FERN_TOKEN`; it fails rather than commit an output missing its
manifest.

Normally you don't regenerate by hand: [`generate-sdk.yaml`](.github/workflows/generate-sdk.yaml)
regenerates both and commits them to your branch whenever `packages/server` or `packages/harness`
changes.

`packages/sdk` is deliberately excluded from the pnpm workspace. The SDK has no runtime dependencies,
but it does carry generated devDependencies (Vitest, Biome, TypeScript), and reconciling those with
`pnpm-lock.yaml` on every regeneration would break `pnpm install --frozen-lockfile` in CI.

## Library imports

```ts
import { AgentThread } from '@truefoundry/utils/core';
import { Sessions } from '@truefoundry/utils/agent-session';
```

Or namespaced:

```ts
import { core, agentSession } from '@truefoundry/utils';
```

Server-only deps (`hono`, `@hono/node-server`, `@hono/swagger-ui`, `yaml`) live in `packages/server` and never reach library consumers.
